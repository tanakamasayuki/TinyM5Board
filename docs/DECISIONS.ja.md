# 決定

内部の記録。日本語のみ。**なぜそう設計したか。**

**何がどうなっているか**は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md)、
**どこまでが責務か**は [REQUIREMENTS.ja.md](REQUIREMENTS.ja.md) にある。

出発点は M5GFX リポジトリにあった調査メモ 4 本。**あれは確定事項ではない**ので、
この文書はゼロベースで決め直した。**メモの提案部分は [research/](research/) から削除し、
事実だけを残してある**ので、方針の記録はこの文書が唯一の正本になる。
メモから変えた点は §2 に残した。

## 1. 決定

### D1. 責務は Board Support 層。M5GFX 相当でも M5Unified 相当でもない

「基板の電源とピン配置を知っている層」を切り出す。

決め手になった観察:

> **Speaker / Mic / IMU / RTC は「ボードを知らなくても」チップドライバがあれば使える。**
> ボード固有なのは「どのピンに何が繋がっているか」と「enable の叩き方」だけ。

一方で**電源は違う**。「AXP192 の LDO2」まで分かってもボードごとに用途が違うので、
**ボードを知らないと使えない**。だから電源はこのライブラリが持ち、
IMU / RTC / Speaker はピン情報を提供するだけにしてドライバを持たない。

| 案 | 却下の理由 |
| --- | --- |
| M5GFX 相当（表示だけ） | 電池が取れない。バックライトも半分は PMIC 経由なので結局 PMIC を触る |
| M5Unified 相当（全部） | Speaker / Mic の enable コールバックが肥大化の主因で、そこを取り込むと同じ道 |

### D2. ボードはビルド時に決め打ちする

M5Unified が重い理由は機能の多さではなく、**60 ボード分をコンパイルして実行時に
どれか 1 つを選ぶ**こと。`M5Unified.hpp:229` で `Display` / `Imu` / `Speaker` / `Mic` が
具象メンバなので、`config_t` のフラグは実行時にスキップするだけでリンクは常に走る。

決め打ちにすると、**やることを増やしても実体化するのは 1 ボード分だけ**になる。

> **やる量ではなく「実行時に選ぶかどうか」が重さを決める。**

M5Atom が「全部やる」のに軽かったのは 1 ボード分しか持たなかったからで、
個別ライブラリ時代の問題は重さではなく**移植できないこと**だった。
**目指すのは M5Unified ではなく「移植できる M5Atom」。**

### D3. GFX ライブラリに依存しない

画面ありボードでは「他の GFX とも使える」という利点にすぎないが、
**画面なしボード 29 機種では必須要件になる。**

`M5GFX.cpp:3318` に、画面なしボードは M5GFX の守備範囲外だと明記されている。
つまり現状の選択肢は M5Unified だけで、それを入れると `M5GFX Display;` が
具象メンバなので**画面が無いのに M5GFX が丸ごとリンクされる**。
Atom Lite の電池電圧を読むためにグラフィックスライブラリをリンクすることになる。

「GFX 非依存」がここで初めて利点ではなく目的になる。

### D4. 停止則は「ビルド時に確定できることだけを持つ」

責務の線をどこに引くかで、次の候補があった。

| 候補 | 問題 |
| --- | --- |
| 「電源かデータか」 | Speaker の EN ピンのような境界例で毎回議論が再燃する |
| 「立ち上げか、デバイス利用か」 | 同じ。どちらも解釈の余地がある |
| **「ビルド時に確定できるか」** | ✅ |

解釈の余地がある基準は、境界例で必ず「便利かどうか」が勝つ。
そして**中間を選ぶと「全部やる」に近づく。** 便利さは常に足す方向にしか働かないため。

「ビルド時に確定できるか」は **D2 の決め打ちから自動的に出てくる**規則なので、
守るために追加の意志を必要としない。「便利だから足す」が理由として使えなくなる。

増殖しない理由も説明できる。**確定する情報は回路図に書いてあることで有限。**
増殖するのは機能のほうで、機能は「実行時に何かを調べる」ことから始まる。
そこを閉じておけば線は自然に止まる。

### D5. ボード内の個体差は、安全に問い合わせられる場合に限り実行時に確かめてよい

D4 の唯一の例外。Core2 の PMIC は AXP192 / AXP2101 で割れており、
**電源もバックライトも別物**になるので、持たないわけにはいかない。

条件を 3 つすべて満たすときだけ許す。

1. **ボードは既に確定している。** 候補を試すのではない
2. **同じバス・同じアドレスの ID レジスタを読むだけ**で判別できる
3. **外れても何も壊さない。** ピンの状態を変えない、書き込まない

M5GFX の autodetect はこれを満たさない。あれは候補のボードを順に試すので、
外れたボードのピンを触ることになり、`pin_backup_t` で退避する仕組みが要る。

> **候補を試すのではなく、居るものに名乗らせる。**

D11 で「自動判定をしない」と決めたが、あれは*どのボードか*の判定で、
理由は「ボードが一覧に無いので代わりに近いものを選ぶ」が起きること。
ここはボードが明示されている上での部品確認なので、その失敗モードが存在しない。

**条件を緩めると M5GFX の autodetect に戻る**ので、3 条件は文書で縛る。

**実装した結果**（`src/TinyM5Board/PowerCore2.h`）:
アドレス `0x34` の `reg 0x03` を**1 回だけ**読んで分岐する。
各ドライバに順番に `probe()` させると同じレジスタを 2 回読むことになり、
**実機がやらない「失敗した検出」がトレースに残る**ので、
判別は上位で 1 回だけ行う形にした。

両ドライバをリンクする代金は**実測 480〜776 バイト**
（AXP192 に固定した場合 / AXP2101 に固定した場合との差、arduino-esp32 3.3.11）。
4 MB のボードで、これを惜しんで筐体を開けさせる理由はない。

### D6. IMU / RTC のチップ種別は持たない

**「このボードの IMU は MPU6886」は成立しない。**
同じ機種名で世代によって載っているチップが違い（Core2 v1.1 と v1.3 がそう）、
ユーザー自身も開けてみないと分からない。

D5 の 3 条件は満たせなくもないが、**D4-3（確定しないものへの対処は 2 つだけ）**で
詰まる。「別ボードとして分けてユーザーに選ばせる」が使えない —— ユーザーが選べないため。
したがって**持たない**。

ピンとバスまでは確定するので渡す。ユーザーは順に初期化するか、アドレスで確認する。

一度これを認めると、次は「アドレスも返して」「じゃあ初期化も」と続き、
**IMU ドライバを持つところまで一直線**になる。そこが D4 で閉じたかった穴。

### D7. パネルの個体差は GFX の仕事

AtomS3（ST7735S / GC9107）、Tab5（3 種）、M5Stack 初代（`invert` のロット差）は
Core2 と同じ構図だが、**D5 の条件 2 を満たさない。**
パネルの ID 読みは SPI バスが上がっていないとできず、Tab5 に至っては
パネルが決まらないと DSI のレーン速度が決まらない。

TinyM5Board は電源とリセットまでをやり、**型番が割れる機種では型番を返さない。**
M5GFX は現に自分で判別しているので、そこは GFX に任せる。

この決定は D1 の「表示だけは諸元を厚く返す」という当初案を崩している。
**表示にも他のデバイスと同じ問題がある**という事実のほうが強かった。

### D8. Core2 はファイル 1 本。名前に版数もチップ名も入れない

D5 で実行時に名乗らせると決めたので、ファイルを分ける必要がない。

分ける案は 2 つあったが、どちらも「利用者が把握できるか」で落ちる。

| 案 | 問題 |
| --- | --- |
| SKU 単位（`Core2V10` / `V11` / `V13`） | 版数を知らない人が多い。しかも **IMU を持たない以上 V11 と V13 は中身が同一**になり、「どっちを選ぶのか」を新たに生む |
| 要素単位（`Core2Axp192` / `Core2Axp2101`） | チップ名は版数よりさらに分かりにくい |

分かっている人は `TINYM5_CORE2_PMIC_AXP2101` を定義すれば片方のコードを落とせる。
**知らない人は何も書かなくてよく、知っている人は締められる。**
両方定義したら `#error` で止める（どちらを意図したのか分からないため）。

### D9. 全 64 機種を対象にする。検証済みフラグを持たない

実機での検証は保証しない。OSS なので、動かない報告が来たら直す。

「実機で確認したものだけ載せる」を選ぶと、**画面なしボード 29 機種という
最大の勝ち筋をほぼ捨てる**ことになる（D3）。

`kVerified` フラグや `#warning` のような身構えも持たない。持つと
「フラグが false のボードは使えないのか」という別の疑問を生むだけで、
実際の信頼性は 1 ミリも上がらない。**保証しないことを README で明示するほうが正直。**

### D10. 入口は `src/` 直下のボードヘッダ 1 本

arduino-cli 1.5.0 で実測した（2026-09-02、[CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §3.1）。

> **ライブラリ解決は `src/` 直下のヘッダ名でしか効かない。**

したがって `#include <TinyM5Board/boards/StickCPlus2.h>` 形式にすると
`#include <TinyM5Board.h>` の併記が必須になる。2 行はサンプルの雛形として冗長だし、
`boards/` という内部構造が入口に露出する。

ボードヘッダを `src/` 直下に置けば 1 行で完結し、しかも
**`#include <TinyM5Board` まで打てば IDE の補完が 64 機種を出す。**
サンプルに全機種を並べられない問題（D19）が、これで実質的に解ける。

`src/` 直下に 64 本並ぶが、IDE のメニューに出るのは `includes=` の 1 本だけなので実害はない。
**`src/` 直下＝入口、`src/TinyM5Board/`＝内部**、という一本の規則にもなる。

`#define` + `<TinyM5Board.h>` も併設する。**ビルドフラグから指定できる**のはこちらだけで、
CI の全機種ビルドと PlatformIO の env 分けがそこに乗る。

### D11. Arduino のボードマクロから自動選択しない

プリプロセッサだけで完結するので実行時コストはゼロだが、それでも入れない。

1. **「ボードが一覧に無いので代わりに近いものを選ぶ」が実際によく起きる。**
   その状態で推測すると、判別ではなく**誤検出の生成器**になる
2. **正しく選んでいても区別がつかない組が実在する。**
   `ARDUINO_M5STACK_CORE2` は v1.0 と v1.1 を区別できない。
   `ARDUINO_M5STACK_ATOMS3` は画面の有無すら区別できない

カバー率も 2/3 しかないので、自動を入口にすると **1/3 のユーザーが最初に `#error` を見る**。
「ライブラリが壊れている」と誤解される。

CI と PlatformIO の需要は D10 のビルドフラグ経路で埋まる。

### D12. Board オブジェクト型。グローバル実体はライブラリが宣言する

```cpp
Board.begin();
Board.Power.getBatteryVoltage();
```

自由関数型（`tinyboard_begin()`）は調査メモ 02 の案だが、あれは C 互換を狙った形で、
**Arduino 専用と決めた時点で理由が消えている。**

グローバル実体をユーザーに書かせる案（`TINYM5_BOARD Board;`）も却下。
1 行増えるうえに名前を自由にできてしまい、**サンプルを雛形にする方針と合わない。**
M5Unified の `M5` と同じく、ライブラリが用意する。

グローバルコンストラクタでハードは触らない。メンバは `constexpr` で構築され、
実際の初期化は `begin()` まで遅延する。

### D13. グローバル名を `M5` にしない

**決定的な理由:** M5Unified は `M5Unified.cpp:58` で `m5::M5Unified M5;` を
**実体として定義**している。同名にすると、M5Unified に依存する公式 Unit ライブラリを
1 つ入れただけで衝突する。**ライブラリを 2 つとも使いたいわけではなく、
Unit ライブラリを 1 個追加しただけで起きる**ので、ユーザーは原因にたどり着けない。

もう 1 つ。`M5.Display` も `M5.Imu` も `M5.Speaker` も持たない以上、
`M5.` で始めても**コピペしたスケッチの大半は通らない。**
「M5. なんだから動くはず」という期待を作って裏切る形になる。
名前が違えば、最初から別のライブラリだと分かる。

名前は `Board`。責務を語っており、`Board.Power.getBatteryVoltage()` は読みやすい。
ただし `Board` も一般的な語なので、`TINYM5_NO_GLOBAL_BOARD` で抑止できるようにして
逃げ道を残す。

### D14. `Board.begin()` はできるだけ初期化する

**TinyGFX の D24（初期化済みインスタンスを受け取る）と意図的に違える。**

TinyGFX は**ピンを知り得ない**から受け取るしかない。TinyM5Board は
**ピンを知っていることが存在理由そのもの**なので、同じ原則を適用すると
一番の価値を捨てることになる。

`Serial` / `Wire` / `Wire1` / 電源レール / LCD リセット / バックライトまで全部やる。
最初に呼ばれるものなので、既存の設定を壊しても実害が小さい。
**壊れて困る人は `begin()` の後で初期化し直せる。**

**`Wire.begin()` を呼ぶことは M5GFX の罪とは別物。**
M5GFX が問題なのは `Wire` をバイパスして I2C ペリフェラルのレジスタを直叩きすること
（`periph_module_enable` + `dev->command[]`）で、同じポートで `Wire` を使うと衝突する。
標準 API を正しいピンで呼ぶのは共存を壊さない。

降り口（`KeepSerial` / `KeepI2c`）は用意する。

### D15. `Board.update()` を持つ

M5Unified が `M5.update()` を必要とするのはボタンの状態機械があるから。
コアが持つ他のものはすべてオンデマンド読み出しで済む。

それでも持つのは、**`wasPressed()` が無いと結局全員が自分で書く**から。
1 個あたり RAM 十数バイトで、ESP32 では入れて損がない（D18）。

**PEK のボードではレート制限する。** StickC / StickC Plus は電源ボタンが PMIC 側なので、
`update()` が I2C トランザクションを発生させる。デバウンス間隔と同じ周期に制限する。

### D16. 名前は M5Unified に寄せる。合わせられない箇所を明示する

基準: **どんな名前でもいいものは合わせる。構造が違うものは合わせない。**
戻り値の型も、合わせない理由がないものは合わせる。

対応表は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §7。合わせない箇所は 2 つだけ。

- `getExtVoltage()` の `float` → 整数（D22）
- `M5.Display.setBrightness()` → `Board.Backlight.set()`（D17）

### D17. バックライトは `Board.Backlight` に置く。`Board.Display` を作らない

M5Unified で明るさを変えるのは `M5.Display.setBrightness()` で、**Display の上にある。**

`Board.Display` を作れば綴りは一致するが、**`fillScreen()` が期待される名前になる。**
実際には諸元と明るさしか持たないので、名前が嘘をつく。

「M5Unified から来た人が探せない」という問題は README の対応表 1 行で埋まる。
「`Board.Display` が描けない」という問題は README では埋まらない。後者を避けた。

### D18. ボタンとデバウンスはコアに入れる —— 停止則の例外

D4 に照らすと `digitalRead` は「データの読み書き」だが、入れる。理由を明記しておく。

**ボード知識なのはピンと極性だけで、ドライバと呼べるものがない。** そして決定的なのは、
**StickC は電源ボタンが PMIC の PEK で GPIO に出ていない**こと。隣の Plus2 は GPIO。

| ボード | BtnA | 電源ボタン |
| --- | --- | --- |
| StickC / StickC Plus | `G37` | **AXP192 PEK（GPIO が無い）** |
| StickC Plus2 | `G37` | `G35`（ただの GPIO） |

**同じ「電源ボタン」が隣り合う機種で PEK と GPIO に分かれる。**
電池が「PMIC か ADC か」で分かれるのとまったく同じ構図で、
この差を吸収できる層はボード層しかない。

RGB LED も同じ理由で例外にするが、**ピンと個数まで**。
WS2812 のドライバはボード非依存なので持たない。

### D19. 群を正式な概念にする。群と機能フラグを混ぜない

**群 = 製品名**（`Core` / `Stick` / `Atom` / `Stamp` / `Paper` / `Unit` / `Other`）。
ユーザーは自分のボードを製品名で認識しているので、探す軸は製品名が一番迷わない。

**動く / 動かないは機能フラグ**（`kHasDisplay` / `kHasBattery` / `kHasBacklight`）。

混ぜてはいけない。Atom 系には画面ありの AtomS3 と画面なしの AtomLite が両方いる。
群を機能で切ると製品名とズレて、かえって自分のボードを探せなくなる。

これで「Atom Lite では Battery サンプルは動きません」を個別に書く必要がなくなり、
**表で一目で分かる**。`kHasBattery` はコンパイル時定数なので、
サンプル側が `#error` で親切に止めることもできる。

### D20. サンプルが実質のドキュメント。軸は機能、ボードは差し替える 1 行

「最低限＋サンプルを充実させて雛形的に使う」という方針の帰結。

**64 機種分のサンプルは作れない**し、作れば必ず「自分のボードのが無い」が起きる。
機能別なら、**同じサンプルがどのボードでも動くこと自体がライブラリの主張**になる。

**1 本目は画面を使わない。** 画面を使うと**画面なしボード 29 機種で成立しない**。
本命の領域（D3）が最初のサンプルから外れるのは筋が悪い。
1 本目は「立ち上げて、生きていることが Serial で分かる」最小形にする。

Buttons / Battery / Backlight のサンプルは、中身が
**「PMIC 機でも GPIO 機でも同じ書き方になること」の実演**になる。
それがこのライブラリの存在意義（D18）なので、サンプルが見せないと伝わらない。

ボード選択はコメントアウトの一覧で見せる。**編集する場所が見えていること**が
雛形として一番効く。全 64 機種は並べられないので**群の代表 1 機種ずつ**にし、
残りは IDE の補完（D10）と README に任せる。

### D21. `library.properties` の `depends` に GFX を書かない

書くと Library Manager 経由で入れた全員に GFX が付いてきて、
**GFX 非依存という主張がそこで崩れる**（D3）。

表示サンプルだけが `sketch.yaml` の `libraries` で GFX を要求する。
TinyGFX の `M5StackBasic` が profile を持っているのと同じやり方。

### D22. float を使わない

**M5 の新しめのボードは RISC-V が多く、FPU が無い**（StampC3 / NanoC6 / UnitC6L /
NessoN1 / ToughC5 / CoreMatrix / NanoH2 / StampC5 / StampC6）。
float を使うと soft-float ライブラリが入り、実行も遅い。

電圧・電流・充電まわりの計算はすべて整数で行う。分圧比のような小数は
`ratioX1000 = 2000` のように整数で持つ。

M5Unified の `getExtVoltage()` が `float` を返しているのは、ここで合わせない箇所になる。

### D23. 文書と言語の規定

TinyGFX と同じ 3 段。兄弟プロジェクトと揃える。

| 区分 | 言語 |
| --- | --- |
| 使う人が読むもの（README / API / examples / GUIDE） | 日英 |
| 内部の記録（`docs/*.ja.md`） | 日本語のみ |
| **コード中のコメント** | **英語のみ** |

`tools/bump_version.py` と `.github/workflows/release.yml` は
[arduino-library-release-toolkit](../../arduino-library-release-toolkit) からコピーし、
**個別編集しない。**

### D24. 上流は取り込み時の資料。通ったら凍結し、以後は追わない

ボードを追加するときは M5GFX / M5Unified /
[variants_collector](https://github.com/tanakamasayuki/variants_collector) を読んで値を起こす。
**通ったらゴールデンとして凍結し、CI からは上流を一切参照しない。**

実地の経験による判断。variants_collector は定期取得で上流と突き合わせているが、
**上流の列が増えるたびに壊れている。** 検証したいのは自分のコードであって上流の形ではないので、
壊れる原因を外部に置くのは割に合わない。

したがって次の 2 つは**やらない**。

- 期待値に M5GFX のソース行のハッシュを埋めて「上流が変わったら知らせる」
- ピン表を M5Unified の `_pin_table_*` と定期的に突き合わせる

どちらも「上流に追随する」ための仕掛けだが、**過去のボードは基本的に更新しない**方針なので、
追随できても使い道がない。守るべきは**「今の M5GFX と一致しているか」ではなく
「一度通った状態から変わっていないか」**。

動かない報告が来たときに、そのボードだけ直す（D9 と同じ立場）。

### D25. 初期化列はホスト実行のゴールデンで固定する

host-arduino-core 1.5.0 の**バス観測ポート**を使う。GPIO（`HostBus.h` の
`setPinWriteHook` / `setPinModeHook` / `setPinReadHook`）、I2C（`Wire.setWriteHook` /
`setReadHook`、トランザクション単位）、SPI（`SPI.setTransferHook`）が揃っており、
**`Board.begin()` が触るものは全部見える。**

`setReadHook` で応答を差し込めるので、**個体差を実行時に確かめる設計（D5）を
ここでしか検証できない。** 実機は Core2 の片方の版しか持っていないため。

順序も含めて固定する。POWER_HOLD が最初でないと実機で電源が落ちるので、
順序は結果と同じくらい重要。

**「ホストで M5GFX を走らせて初期化列を取る」は構造的に不可能。**
`M5GFX.cpp:80` の `#if defined(ESP_PLATFORM)` がボード別処理を丸ごと囲んでおり、
ホストビルドでは `autodetect()` が「`Panel_sdl` を作ってウィンドウの寸法と
タイトルを決めるだけ」の別関数に差し替わる。M5Unified も `I2C_Class` が呼ぶ
`m5gfx::i2c::*` の SDL 実装が全部エラーを返すスタブで、`Power_Class` は
`M5UNIFIED_PC_BUILD` で無効化されている。詳細は
[TEST_PLAN.ja.md](TEST_PLAN.ja.md) §6。

### D26. カタログはデータだけを持つ。手順はコードに残す

ピンや群はデータなので表に入るが、レール投入の**手順**は入らない。
StickC は AXP192 の 1 レジスタだが、StopWatch は M5IOE1 の 5 ピンを個別に設定して
リセットパルスを打ち、Tab5 は PI4IO 2 個に 5〜7 レジスタずつ書く。
表で表現しようとすると**任意のレジスタ列を書ける記述形式が要り、表が DSL になる。**

上流も同じ結論に達している。M5Unified は `_pin_table_*`（データ）と
ボードごとの `switch`（手書きコード）に分かれていて、表に押し込もうとした形跡がない。

ただし 2 つ条件を付ける。

**1. 手順は省略可にする。** POWER_HOLD・レール投入・LCD リセット・ボタン・
バックライトは列から導出できるので、既定は生成に任せる。
書くのは収まらないボードだけ。

**2. 手順にレジスタ番号を書かない。** ボード側は「どのレールを使うか」だけを言い、
`0x12` も `0x4D` もチップドライバに閉じ込める。
これで手順がボードごとに 2〜5 行に収まり、**逃げ道が表を壊さない。**

詳細は [BOARD_CATALOG.ja.md](BOARD_CATALOG.ja.md)。

### D27. 照会できるピンは 4 つだけ

内部 I2C / Port A（外部 Grove）/ RGB LED / POWER_HOLD。

M5Unified の `getPin()` は Port A〜E・SD 6 本・MBUS 30 本まで持つが、
**IMU / RTC / Speaker / Mic は持っていない**（`M5Unified.hpp:26`）。
ドライバ側に焼き込まれている。

| | 範囲 | 判断 |
| --- | --- | --- |
| 採用 | 内部 I2C / Port A / RGB LED / POWER_HOLD | 転記元が構造化データとして存在する |
| 見送り | Port B〜E / SD 6 本 | 転記元はあるが Core 系限定。**後から列を足せる** |
| 却下 | IMU / RTC / SPK / MIC | **構造化された転記元が無い。** 回路図から 64 機種分を起こすことになる |

判断基準は作業量ではなく**間違ったときの被害**。ピン表は「調べる手間を省く」ための
情報なので、間違っていると調べるより悪い。一度に多数のピンを埋めると、
検証できない値が大量に入る。

IMU はさらに、**チップ種別が確定しない**（D6）のでピンだけ出しても
使う側はプローブが要る。出す価値が最初から薄い。

### D28. ピンは `constexpr` 定数が正。`getPin()` は移行用に併設する

ボードが決め打ちなので、ピンは**コンパイル時定数**として持てる。

```cpp
Wire.begin(TinyM5BoardStickCPlus2::kI2cSda, TinyM5BoardStickCPlus2::kI2cScl);
Board.getPin(TinyM5::Pin::RgbLed);   // M5Unified からの移行用。同じ値に畳まれる
```

`getPin()` は照会する対象が 4 つしかないので `switch` 1 本で、
定数に畳まれて実行時コストはゼロ。**両方あって困らない**ので、
名前を合わせられるものは合わせる方針（D16）に従って併設する。

### D29. Arduino コアは個別インストールせず、`sketch.yaml` の profile で入れる

`arduino-cli core install` を使わない。**バージョンを固定できるのが profile だけ**のため。

```yaml
profiles:
  atomlite:
    fqbn: esp32:esp32:m5stack_atom
    platforms:
      - platform: esp32:esp32 (3.3.11)
        platform_index_url: https://espressif.github.io/arduino-esp32/package_esp32_index.json
    libraries:
      - dir: ../../
```

`arduino-cli compile --profile atomlite` が、指定のバージョンを
**`~/.arduino15/internal/<packager>_<arch>_<version>_<hash>/` へ隔離して**入れてからビルドする
（実測、arduino-cli 1.5.0）。`packages/` は汚れず、**バージョンごとに別の実体**になる。
CI もローカルも同じものが入り、**コアが上がって黙って結果が変わることがない。**

テストが生成するスケッチも同じ形にする。CI のワークフローに
`core install` を書かない。

### D30. 最初のボードは AtomLite

v1 のスコープは「最終的にはなるべく多く」だが、**起点は作りやすいものにする。**

AtomLite を選ぶ理由:

- 画面なし・電源ハードなし・ボタン 1 つ・RGB LED 1 つ。**骨格を通すのに最小**
- しかも**本命の領域**（画面なしボード 29 機種、D3）の代表そのもの
- 表示や PMIC が無いので、`kHasDisplay` / `kHasBattery` が `false` の側を最初に踏める

ただし**「初期化一切なし」ではない。** `M5Unified.cpp:2299` に、
CH552 が GPIO0 に 4V をかけて WiFi 感度が落ちる問題への対策として
GPIO0 を出力 HIGH にする処理がある。

これは役割名では表現できない一点ものなので、**`power_on` の逃げ道（D26）が
最初のボードから必要になる。** 逃げ道が本当に要ることを、起点で確認できる。

### D31. 機能の有無はプリプロセッサのマクロでも出す

`kHasBattery` のような `constexpr` 定数だけでは足りない。

```cpp
if constexpr (TINYM5_BOARD::kHasBattery) {
  Board.Power.getBatteryVoltage();   // ← 画面なしボードでコンパイルエラー
}
```

**テンプレートの外では、`if constexpr` の捨てられた枝も名前解決される。**
`Board.Power` が存在しないボードでは、実行されない側に書いてもコンパイルが通らない。

無い機能を no-op で埋めない（D5 / REQUIREMENTS §7）と決めた以上、
移植できるサンプルを書くには `#if` が要る。だから
`TINYM5_HAS_BATTERY` / `_DISPLAY` / `_BACKLIGHT` / `_EXTERNAL_I2C` を
ボードヘッダから出す。

`constexpr` 定数のほうも残す。実行時の分岐や `static_assert` にはそちらが要る。
**どちらもカタログの同じ列から生成する**ので、食い違いようがない。

**ボタンにも要る。** Tough は GPIO のボタンを 1 つも持たない（A/B/C はタッチ領域）、
StickC の電源キーは PMIC の中、Station は 3 つ —— **ボード間で一番ばらつく。**
`TINYM5_HAS_BTN_A` / `_B` / `_C` / `_PWR` と `TINYM5_HAS_RGB_LED` も出す。

実装中に Tough を追加したところ、`Board.BtnA` を書いたサンプルが
**コンパイルエラーで落ちた。** 意図どおりの挙動だが、
マクロが無ければ移植できるサンプルが書けないことがそこで分かった。

### D32. `begin()` のボード固有手順は、電源チップを立ち上げた後に走らせる

`power_on`（D26 の逃げ道）を呼ぶ位置は、**チップドライバを繋いだ後**でなければならない。

Tough の `power_on` は AXP192 の IO4（LCD リセット）と IO1（タッチリセット）を
叩くが、`Power.begin()` より前に呼ぶと **I2C が 1 バイトも出ずに素通りする。**
実装中に一度この順で書いて、ゴールデンに I2C 行が現れないことで気づいた。

順序は [CORE_DESIGN.ja.md](CORE_DESIGN.ja.md) §5.1 に固定した。

### D33. レール電圧はレールを入れる前に設定する

`rails` と `rail_mv` を分けて、**電圧 → 投入**の順で `begin()` が処理する。

M5GFX がこの順（`0x28` に 3300 mV → `0x12` で LDO2 ON）なのには理由がある。
**先に投入すると、リセット値の電圧が一瞬パネルに掛かる。**
実装中に逆順で書いてゴールデンを取り、M5GFX と並べて気づいた。

### D34. テストは群ごとに分けて並列化する

`tests/begin/` を `begin/<群>/<ボード>/` の形にして、**群を CI の matrix の軸**にする。

```yaml
matrix:
  family: ${{ fromJson(needs.catalogue.outputs.families) }}
run: uv run pytest "begin/${{ matrix.family }}" --profile host
```

軸は `tools/gen_boards.py --families` がカタログから出すので、
**群を足しても workflow を触らなくてよい。**

必要な理由は所要時間。`begin` は 1 本ごとにスケッチをビルドして実行するので、
**機種数に線形に伸びる。** 11 スケッチで約 8 分、60 機種なら 30 分を超える。

ローカルでも同じ単位で絞れる（`pytest begin/Stick` で約 2 分）ので、
普段は自分が触った群だけを回せばよい。

`--check`（生成物が最新か）は matrix の**前段に 1 回だけ**置く。
生成物が古いと、後続のジョブは全部「違うものを検査した」ことになるため。

### D35. 「何が挿さっているか」は調べない。既定を選んで、明示で切り替える

CoreS3 の立ち上げで、M5GFX は **GPIO 35/36/37 にプルアップを掛けて読み**、
効いていなければ AW9523B の VBUS 5V 出力を有効にする（USB ホストモジュールなど、
5V が出ていないと信号線から電流を吸う組み合わせがあるため）。

**これは D5 の例外に当たらない。** D5 が許すのは「ボードが確定した上で、
同じバス・同じアドレスの ID レジスタを読んで**チップに名乗らせる**」ことで、
ここで調べているのは**何が挿さっているか**。ビルド時に確定しない
（D4 の停止則）し、判別のために SPI バスのピンを一時的に触ってもいる。

→ **5V 出力を入れない側を既定にする**（素の CoreS3 はプルアップが効いている）。
必要な人は明示的に有効化する。

一般則として書いておく:

> **接続されている周辺機器の有無は調べない。**
> 既定は「何も挿さっていない」側に倒し、切り替えは明示的な API で行う。

これを緩めると、`_detect_i2c_device` と `pin_backup_t` を持つ方向、つまり
M5GFX の autodetect に戻る。

### D36. クリック回数は M5Unified と同じ状態機械で数える。読まなかった `update()` は何も報告しない

`wasClicked` / `wasSingleClicked` / `wasDoubleClicked` / `getClickCount` を、
M5Unified の `Button_Class` と**同じ状態遷移**で実装する
（`state_nochange` / `clicked` / `hold` / `decide_click_count` の 4 状態）。

移植のためだけではない。**クリック回数は押した瞬間には決まらない**ので、
「2 回目が来ないと確定しない」ことをどこかで表現するしかなく、
上流はそれを「最後のクリックから hold 閾値だけ静かなら確定」で解いている。
別の解き方を発明しても、**閾値がもう 1 つ増えるだけ**で良くならない。

分かったこと 2 つ。

**押しっぱなしからの離しはクリックではない。** そこで数えると、
長押しが必ず「長押し + クリック」の 2 つになる。上流も `oldPress == 1`
（保持に昇格していない押し）からの離しだけを数えている。

**間引いた `update()` はエッジを消す。** I2C 越しのボタン（PMIC の電源キー、
エキスパンダのピン）はデバウンス間隔に 1 回しか読まない。読まなかった回で
前回の値を残すと、**1 回の押しが `wasPressed()` で何度も取れる。**
読み飛ばす経路でも `_oldPress` を畳み、報告済みのクリック回数を捨てる。

検査は `tests/unit/Button/`。時刻は `update(msec)` の引数なので、
**600 ms の長押しも実時間 0 秒**で、結果はマシンの速さに依存しない。

**代金はフラッシュ 160 バイト**（AtomLite / ボタン 1 つ / `examples/Hello` /
arduino-esp32 3.3.11 で 294,280 → 294,440 B）。
