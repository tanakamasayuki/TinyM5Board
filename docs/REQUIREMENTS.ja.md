# 要件

内部の記録。日本語のみ。**何を作るライブラリで、どこまでを責務にするか。**

たたき台。確定していない項目には「**暫定**」と書く。

## 1. 一言でいうと

> **M5 のボードを、GFX ライブラリを引き込まずに立ち上げるためのライブラリ。**

ボードはビルド時に決め打ちする。電源を入れ、リセットを解き、ピン表を公開するところまでを
持つ。画面に描くことも、IMU から値を読むこともしない。

目指すのは**「移植できる M5Atom」**であって、軽い M5Unified ではない。

## 2. 背景

M5 の既存ライブラリには、構造から来る穴が 3 つある。

**1. 電源管理を提供するのが実質 M5Unified しかなく、それは M5GFX に依存する。**
「電池残量が欲しいだけ」でグラフィックスライブラリを丸ごとリンクすることになる。
汎用の AXP192 ライブラリは存在するが、**どのレールが何に繋がっているかはボード固有の知識**
なので、結局ユーザーが自分で調べることになる。

**2. 画面なしボード 29 機種は、M5GFX が明示的に降りている領域。**
`M5GFX.cpp:3318` にそう書いてある。

> Board identity of display-less boards is resolved by M5Unified (eFuse-based),
> not here. **Do not add board detection here.**

つまり画面なしボードで電源管理をしたければ、現状の選択肢は M5Unified しかない。
そして M5Unified を入れると `M5GFX Display;` が具象メンバなので、
**画面が無いのに M5GFX が丸ごとリンクされる。**

**3. Arduino はライブラリの `src/` 以下の `.cpp` を、使っていなくても全部コンパイルする。**
M5Unified は `.cpp` が 40 本ある。IMU も RTC も Speaker も Mic も、使わなくてもビルドされる。

### 2.1 根が深いのは 3 つ目

M5Unified が重い理由は機能の多さではなく**構造**にある。`M5Unified.hpp:229` で
`Display` / `Imu` / `Speaker` / `Mic` がすべて具象メンバとして宣言されているので、
`config_t` のフラグは**実行時の初期化をスキップするだけ**で、コンパイルとリンクは常に走る。

機能を削れば直る問題ではない。god オブジェクト設計の帰結。

> **重さを決めるのは「やる量」ではなく「実行時に選ぶかどうか」。**

裏返すと、**ボードを決め打ちにすれば、やることを増やしても実体化するのは 1 ボード分だけ**に
なる。M5Atom が「全部やる」のに軽かったのは 1 ボード分しか持たなかったからで、
個別ライブラリ時代の問題は重さではなく**移植できないこと**だった。

**移植性を捨てずに軽さを取り戻す**のがこのライブラリの位置づけになる。

## 3. 設計原則

| 原則 | 内容 |
| --- | --- |
| **ビルド時に確定することだけを持つ** | 責務の停止則。§4 |
| **god オブジェクトを持たない** | 実体化するのはビルド時に選んだ 1 ボード分だけ |
| **ヘッダオンリー** | `.cpp` を 1 本も置かない。**include しなかったヘッダは 1 秒も食わない**。`--gc-sections` はフラッシュしか節約しないが、ヘッダオンリーは**コンパイル時間そのもの**を節約する |
| **opt-in include** | 電源チップ・バックライト方式・IO エキスパンダは個別ヘッダ。ボードヘッダが必要なものだけを引く |
| **GFX に依存しない** | コアは GFX ライブラリの名前を 1 つも知らない。連携は opt-in の adapter ヘッダに閉じる |
| **整数演算のみ** | RISC-V 機に FPU が無い。§5.2 |
| **グローバルコンストラクタでハードを触らない** | `begin()` まで遅延する。初期化順序の問題を作らない |
| **ループ内で動的確保しない / `String` を返さない** | ヒープ断片化は ESP32 でも普通に起きる |
| **名前は M5Unified に寄せる** | 決めの問題でしかない箇所は、既存ユーザーが迷わない名前にする。合わせられない箇所は無理に合わせない |
| **ボード情報はカタログから生成する** | 手で 64 機種を並べると、追加のたびに漏れる |

## 4. 責務境界

### 4.1 停止則

> **ビルド時に確定できることだけを持つ。実行時に調べないと分からないことは持たない。**

「電源かデータか」「立ち上げかデバイス利用か」といった基準は、どちらも解釈の余地がある。
解釈の余地があると、境界例で毎回「便利かどうか」が勝ち、線は必ず内側へ動く。

この停止則は**最初に決めた「ビルド時決め打ち」から自動的に出てくる**ので、
守るために追加の意志を必要としない。「便利だから足す」が理由として使えなくなる。

### 4.2 当てはめ

| | ビルド時に確定するか | 扱い |
| --- | --- | --- |
| ピン番号・極性 | する | **持つ** |
| 電源レールの接続先と投入手順 | する | **持つ** |
| リセットの経路（GPIO / PMIC / エキスパンダ） | する | **持つ** |
| バックライトの方式と輝度カーブ | する | **持つ** |
| SD とバスを共有するボードのモード落とし | する | **持つ** |
| 表示のピン・バス・周波数 | する | **持つ** |
| IMU / RTC / Speaker のピンとバス | する | **持つ**（ピンまで） |
| **IMU / RTC のチップ種別** | **しない**（世代で変わる） | **持たない** |
| **パネルの型番**（AtomS3 / Tab5 / M5Stack のロット差） | **しない** | **持たない** |
| **Core2 の PMIC**（AXP192 / AXP2101） | **しない** | §4.4 |

「このボードの IMU は MPU6886」は成立しない。**同じ機種名で世代によって載っているチップが違い、
ユーザー自身も開けてみないと分からない。** だからチップ種別は持たず、ピンとバスまでを渡して、
順に初期化するかアドレスで確認してもらう。

### 4.3 確定しないものへの対処は 2 つしかない

1. **別ボードとして分けて、ユーザーに選ばせる** — 見分けがつく場合のみ
2. **持たない**

「実行時に調べる」という第三の道は、決め打ちを捨てることなので取れない。

IMU は 1 が使えない（ユーザーも見分けられない）ので 2 になる。

### 4.4 唯一の例外 — ボード内の個体差

Core2 の PMIC は AXP192 と AXP2101 で割れており、**電源もバックライトも別物**になる。
持たないわけにはいかない。

> ボードはビルド時に決め打ちする。**ボード内の個体差は、安全に問い合わせられる場合に限り**
> 実行時に確かめてよい。

「安全に問い合わせられる」の条件を厳密に定める。**3 つすべてを満たすときだけ。**

1. **ボードは既に確定している。** 候補を試すのではない
2. **同じバス・同じアドレスの ID レジスタを読むだけ**で判別できる
3. **外れても何も壊さない。** ピンの状態を変えない、書き込まない

AXP192 / AXP2101 はこれを満たす（どちらも I2C `0x34`、`reg 0x03` が `0x03` / `0x4A`）。

M5GFX の autodetect はこれを満たさない。あれは**候補のボードを順に試す**ので、
外れたボードのピンを触ることになり、`pin_backup_t` で退避する仕組みが要る。
**候補を試すのではなく、居るものに名乗らせる。** 質が違う。

パネルの型番判別も満たさない。SPI バスが上がっていないと ID を読めず、
Tab5 に至ってはパネルが決まらないと DSI のレーン速度が決まらない。
**パネルの個体差は GFX の仕事**にする。M5GFX は現に自分で判別している。

### 4.5 例外を認めるもの — 理由込みで明記する

停止則の外にあるが、入れると決めたもの。**なし崩しで増えないよう理由を書く。**

| | 理由 |
| --- | --- |
| **ボタン** | `digitalRead` はデータの読み書きだが、ボード知識はピンと極性だけでドライバと呼べるものがない。しかも**StickC は電源ボタンが PMIC の PEK で GPIO に出ていない**。隣の Plus2 は GPIO。この差を吸収できる層はここしかない |
| **ボタンのデバウンスとエッジ検出** | 状態機械を持つのでコストはあるが、1 個あたり RAM 十数バイト。ESP32 では入れて損がない。`wasPressed()` が無いと結局全員が自分で書く |
| **RGB LED** | Atom 系では実質そのボードの唯一の出力。ただし**ピンと個数まで**。WS2812 のドライバは持たない |

### 4.6 持たないもの

| | 理由 |
| --- | --- |
| ディスプレイドライバ | GFX の領分。**諸元データだけ渡す** |
| IMU / RTC / Speaker / Mic / Touch / SD のドライバ | ボード非依存なので、ボード層が持つ理由がない。**ピンとバスだけ渡す** |
| 実行時のボード判別 | 決め打ちなので不要。§4.4 の個体差確認とは別物 |
| Arduino ボードマクロからの自動選択 | §6.2 |
| `M5.Display` / `M5.Imu` 相当の名前 | 持たないものに**no-op を置かない**。無い名前は無いままにする |

## 5. 対象環境

**ESP32 系のみ。** TinyGFX と違い、AVR や CH32 は対象外。

### 5.1 緩めてよいところ

ESP32 では実質タダなので、TinyGFX ほど切り詰めない。

| | 理由 |
| --- | --- |
| 仮想関数・継承 | vtable は数十バイト |
| クラス数 | 責務分離を優先してよい |
| `constexpr` テーブル | フラッシュに数百バイト |
| コメントとドキュメント | コストゼロ |

ただし**ヘッダオンリーと opt-in include は緩めない。** あれはフラッシュではなく
**ビルド時間**の話であり、「気軽に実験できる」はそこで決まる（§3）。

### 5.2 float を使わない

**M5 の新しめのボードは RISC-V が多く、FPU が無い。**
StampC3 / NanoC6 / UnitC6L / NessoN1 / ToughC5 / CoreMatrix / NanoH2 / StampC5 / StampC6。

| SoC | FPU |
| --- | --- |
| ESP32 / S3 / P4 | あり |
| S2 / C3 / C6 / H2 / C5 | **なし** |

（調査メモ由来。IDF 5.4 の `soc_caps.h` `SOC_CPU_HAS_FPU` による）

float を使うと soft-float ライブラリが入り、実行も遅い。
**電圧・電流・充電まわりの計算はすべて整数で行う。**
分圧比のような小数は `ratioX1000 = 2000` のように整数で持つ。

M5Unified の `getExtVoltage()` が `float` を返しているのは、ここで合わせない箇所になる。

### 5.3 `Wire1` が存在しない SoC がある

**ESP32-C3 は I2C コントローラが 1 個しかない。**

| SoC | I2C 数 |
| --- | --- |
| ESP32 / S3 | 2 |
| **C3** | **1** |
| C6 / H2 | 2 |
| P4 | 3 |

（調査メモ由来。IDF 5.4 の `soc_caps.h` `SOC_I2C_NUM` による）

Arduino-ESP32 の `Wire.h` は `#if SOC_I2C_NUM > 1` で `Wire1` をガードしている。
StampC3 / StampC3U が該当する。さらに ToughC5 / CoreMatrix / NessoN1 は
**内部 I2C と外部 Grove が物理的に同一**。

ボードヘッダは「外部バスがあるか」「内部と共有か」を表現できる必要がある。

なお P4 は I2C が 3 個あるが、`Wire.h` の `#elif SOC_I2C_NUM > 2` は
先行する `#if SOC_I2C_NUM > 1` に吸われて到達しないため **`Wire2` は宣言されない**。
当てにしない。

### 5.4 言語

C++17 が使える見込み（**暫定** — arduino-esp32 3.x の実際の `-std` を確認して確定する）。
TinyGFX の C++11 制約はここには効かない。

## 6. 対象ボード

### 6.1 全機種を対象にする

`boards.hpp` の全 64 機種（表示 35 + 非表示 29）を対象にする。

**実機での検証は保証しない。** OSS なので、動かない報告が来たら直す。
「未検証だから載せない」を選ぶと、**画面なしボード 29 機種という最大の勝ち筋をほぼ捨てる**
ことになるため、そちらは取らない。

検証済みフラグや `#warning` のような身構えも持たない。持つと「フラグが false のボードは
使えないのか」という別の疑問を生むだけで、実際の信頼性は 1 ミリも上がらない。

### 6.2 ボードは明示的に選ぶ。自動判定はしない

Arduino のボード選択から推測することはしない。理由は 2 つ。

1. **「ボードが一覧に無いので代わりに近いものを選ぶ」が実際によく起きる。**
   その状態で推測すると、判別ではなく誤検出の生成器になる
2. **正しく選んでいても区別がつかない組が実在する。**
   `ARDUINO_M5STACK_CORE2` は v1.0 と v1.1 を区別できない

ビルドフラグから指定する道は用意する（§CORE_DESIGN）。CI と PlatformIO の需要はそれで埋まる。

### 6.3 群

ボードは製品名で群に分ける。**Core / Stick / Atom / Stamp / Paper / Unit / その他。**

README の表・サンプルの一覧・CI のビルドマトリクスをこの単位で並べる。
ユーザーは自分のボードを製品名で認識しているので、探す軸は製品名が一番迷わない。

**群と「動く / 動かない」は混ぜない。** Atom 系には画面ありの AtomS3 と
画面なしの AtomLite が両方いる。群を機能で切ると製品名とズレて、かえって探せなくなる。

- **群 = 製品名**（探すための軸）
- **動く / 動かない = 機能フラグ**（`kHasDisplay` / `kHasBattery` / `kHasBacklight`）

### 6.4 ボード ID

独自 enum を定義するが、**数値は
[m5stack-board-id](https://github.com/m5stack/m5stack-board-id) に合わせる**。
M5GFX / M5Unified と値を共有しつつ、依存は作らない。

## 7. 非目標

- **M5Unified 互換を目指さない。** 名前は寄せるが、互換レイヤも互換表も作らない
- **実行時にボードを判別しない**（§4.4 の個体差確認を除く）
- **デバイスドライバを持たない。** IMU / RTC / Speaker / Mic / Touch / SD / ディスプレイ
- **完全な移植性を約束しない。** `#include` を差し替えれば大半が通るが、
  画面なしボードに `Backlight` は無い。**無いものは no-op で誤魔化さず、コンパイルエラーにする**
- **ESP-IDF を対象にしない。** Arduino 専用。I2C 抽象は `TwoWire&` 1 本で済む
- **M5 以外のベンダに広げない。** 必要になったら `TinyBoard` を基底に切り出す

## 8. 最小リリース（v1.0）の合格条件

**暫定。** DEVELOPMENT_PLAN で確定させる。

1. 手元の実機 1 台で `Board.begin()` から `Board.update()` までが通る
2. 同じサンプルが、include 1 行の差し替えで別の群のボードでもビルドできる
3. 画面なしボードで、GFX を 1 バイトもリンクせずに電池とボタンが読める
4. 全機種分のボードヘッダが、単体 include でコンパイルできる
5. `Board.begin()` が発行する I2C のレジスタ列が、期待値と一致することをホストで検査できる
